# Спецификация Native SMB-клиента (SMB1/CIFS) в Movian

> **Провенанс.** Каждое утверждение выведено чтением
> `src/fileaccess/smb/fa_nativesmb.c` и `src/fileaccess/smb/smbv1.h` на
> `movian6` @ `80e6c3617` (2026-08-15) и снабжено ссылкой на строку. Ничего не
> перенесено из более ранних черновиков (PR #194 отклонён, задача #196).

Речь о собственной реализации SMB1/CIFS под схемой `smb://`. Это не тот
бэкенд, что `smb2://` — тот построен на bundled libsmb2 и описан отдельно
(`LINUX_SMB2_BACKEND.md`).

---

## 1. Регистрация и объём возможностей

`fa_protocol_smb` (`fa_nativesmb.c:2928-2944`):

| Поле | Значение |
|---|---|
| `fap_name` | `smb` |
| `fap_flags` | `FAP_INCLUDE_PROTO_IN_URL`, `FAP_ALLOW_CACHE` |
| Чтение | `fap_scan`, `fap_open`, `fap_close`, `fap_read`, `fap_seek`, `fap_fsize`, `fap_stat` |
| Изменение | `fap_unlink`, `fap_rmdir` |
| Расширенные атрибуты | `fap_set_xattr`, `fap_get_xattr` |
| Прочее | `fap_no_parking` |

Форма возможностей нестандартная, и её стоит запомнить целиком: **содержимое
файлов только читается, но удалять файлы и каталоги клиент умеет.** Записи
(`fap_write`), создания каталогов (`fap_makedir`) и переименования
(`fap_rename`) в таблице нет.

`smb_open` (`:2251-2300`) всегда отправляет **одну и ту же заявку**:
`access_mask = 0x20089`, `create_disposition = 1` (открыть существующий),
`share_access = 1`. Открыть файл на запись или создать несуществующий через этот
путь нельзя — форма заявки от `flags` не зависит.

Но сами `flags` не выбрасываются: они уходят в `cifs_resolve` (`:2260`), где
`FA_NON_INTERACTIVE` превращается в `CC_F_NON_INTERACTIVE` и решает, будет ли
авторизация спрашивать пользователя и повторять попытки (`:644`).

Наличие `fap_set_xattr` объясняется тем, что Movian хранит в расширенных
атрибутах метаданные медиатеки.

## 2. Авторизация

Идентификатор записи в связке ключей — `smb:connection:<host>:<port>`
(`:649`), с портом. Домен по умолчанию — `WORKGROUP` (`:636`, `:673`).

Механизм — **NTLMv1**: пароль преобразуется `NTLM_hash()` (`:275`), затем
`lmresponse()` (`:344-350`) считает три раунда DES по 8 байт от 21-байтового
расширенного хеша, используя присланный сервером 8-байтовый вызов
`cc_challenge_key`. NTLMv2, Kerberos и расширенная безопасность не
реализованы.

Три режима подключения, задаются флагами (`:102-104`):

| Флаг | Смысл |
|---|---|
| `CC_F_AS_GUEST` | гостевой вход, минуя запрос учётных данных (`:640`) |
| `CC_F_ANONYMOUS` | пустая сессия, без имени и пароля (`:677`) |
| `CC_F_NON_INTERACTIVE` | не спрашивать пользователя; проба, а не открытие |

## 3. Соответствие операций командам SMB1

Константы команд определены в `smbv1.h:577-587`. **Именование там короткое, не
как в MS-CIFS**: искать `SMB_COM_CLOSE` бесполезно, в коде это `SMB_CLOSE`.

| Функция VFS | Команда | Примечание |
|---|---|---|
| `smb_open` | `SMB_NT_CREATE_ANDX` (0xa2) | Фиксированная заявка, см. раздел 1 |
| `smb_close` | `SMB_CLOSE` (0x04) | |
| `smb_read` | `SMB_READ_ANDX` (0x2e) | Асинхронно, несколько запросов в полёте |
| `smb_seek` | — | Только смещение в `smb_file_t` |
| `smb_fsize` | — | Возвращает `sf->sf_file_size`, полученный при открытии. **В сеть не ходит** |
| `smb_stat` | `SMB_TRANS2` (0x32) / `TRANS2_QUERY_PATH_INFORMATION` (5) | |
| `smb_scandir` | `SMB_TRANS2` (0x32) / `TRANS2_FIND_FIRST2` (1), `TRANS2_FIND_NEXT2` (2) | |
| `smb_unlink` | `SMB_DELETE_FILE` (0x06) | |
| `smb_rmdir` | `SMB_DELETE_DIR` (0x01) | |
| `smb_set_xattr` | `SMB_TRANS2` (0x32) / `TRANS2_SET_PATH_INFORMATION` (6) | `:2604` |
| `smb_get_xattr` | `SMB_TRANS2` (0x32) / `TRANS2_QUERY_PATH_INFORMATION` (5) | `:2677` |
| `smb_enum_servers` | `SMB_TRANSACTION` (0x25), RAP NetServerEnum2, код функции 104 | `:2773-2799` |
| поддержание сессии | `SMB_ECHO` (0x2b) | См. раздел 5 |

Установка соединения дополнительно использует `SMB_NEG_PROTOCOL` (0x72),
`SMB_SETUP_ANDX` (0x73) и `SMB_TREEC_ANDX` (0x75).

## 4. Ошибки

**Отображения статусов SMB в `errno` не существует.** `check_smb_error`
(`:1568-1590`) делает ровно три вещи:

```c
if(errcode) {
  snprintf(errbuf, errlen, "SMB Error 0x%08x", errcode);
  free(rbuf);
  cifs_release_tree(ct, 0);
  return -1;
}
```

то есть форматирует числовой код в текст, освобождает буфер, отпускает дерево и
возвращает `-1`. Отдельные статусы там не разбираются — вызывающий видит строку с
шестнадцатеричным числом.

Одно исключение, и оно вне `check_smb_error`: `smb_set_xattr` разбирает статус
сам и отображает `0xC0000022` в `FAP_PERMISSION_DENIED`, а два статуса
неподдерживаемой операции — в `FAP_NOT_SUPPORTED` (`:2627-2631`). Это
единственная операция бэкенда, чей результат несёт различимую причину отказа.

Единственное различие, которое функция всё же делает, — между ошибкой
протокола и коротким пакетом: первая отпускает дерево с `full = 0`, второй с
`full = 1` (`:1578`, `:1585`), то есть повреждённый ответ рвёт соединение
целиком, а обычная ошибка — нет.

## 5. Поддержание сессии и таймауты

| Параметр | Значение | Где |
|---|---|---|
| `SMB_ECHO_INTERVAL` | **30** (единицы `callout_arm`) | `:55`, взводится на `:1119` |
| `NBT_TIMEOUT` | **30000** мс | `:69`, применяется на `:1181` |

Периодический `cifs_periodic` (`:2731-2749`) отправляет `SMB_ECHO` **с
двухбайтовой полезной нагрузкой `0x13 0x37`** и `pid = 3`. Пустым этот пакет не
является, и по `pid` его ответ отличается от ответов на обычные запросы.

`NBT_TIMEOUT` — предел ожидания ответа на запрос, реализован через
`hts_cond_wait_timeout` на условной переменной соединения.

## 6. Кодировки и размеры

Юникод согласуется на этапе `SMB_NEG_PROTOCOL` и запоминается в `cc_unicode`;
`cc_bpc` хранит число байт на символ — 1 или 2 (`:129-130`). Все имена
проходят через `utf8_to_smb`, а разделители пути переводятся в обратные косые
черты (`backslashify`, `:2267`).

Согласованные с сервером пределы — `cc_max_buffer_size` и `cc_max_mpx_count`
(`:124-125`). **`cc_max_mpx_count` нигде не соблюдается**: он сохраняется при
согласовании и копируется в заявку сессии, но цикл чтения
(`:2375-2399`) ставит в очередь по запросу на каждый кусок в 57 344 байта, ни
разу его не проверяя. Крупное чтение может превысить согласованный с сервером
предел — насколько это достижимо на практике, зависит от того, какой
`max_mpx_count` объявляют реальные серверы, и не измерялось.
