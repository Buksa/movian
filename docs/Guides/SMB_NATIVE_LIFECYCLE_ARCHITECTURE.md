# Архитектура жизненного цикла Native SMB-клиента

> **Провенанс.** Выведено чтением `src/fileaccess/smb/fa_nativesmb.c` на
> `movian6` @ `80e6c3617` (2026-08-15); каждое утверждение снабжено ссылкой на
> строку. Функциональная сторона — в `SMB_NATIVE_SPECIFICATION.md`.

Три уровня владения, вложенных строго: соединение содержит деревья, дерево
содержит открытые файлы. Разрушение идёт снизу вверх и **только по счётчикам
ссылок** — ни один уровень не закрывается по времени.

---

## 1. Структуры

### `cifs_connection_t` (`fa_nativesmb.c:92-149`)

Соединение с сервером. Существенные группы полей:

| Группа | Поля |
|---|---|
| транспорт | `cc_tc`, `cc_hostname`, `cc_port`, `cc_flags` |
| состояние | `cc_status`, `cc_broken`, `cc_errbuf`, `cc_auto_close` |
| поток и синхронизация | `cc_thread`, `cc_cond`, `cc_pending_nbt_requests` |
| сессия | `cc_uid`, `cc_session_key`, `cc_challenge_key[8]`, `cc_domain[64]` |
| согласованное | `cc_unicode`, `cc_bpc`, `cc_ntsmb`, `cc_security_mode`, `cc_max_buffer_size`, `cc_max_mpx_count` |
| владение | `cc_trees`, `cc_timer`, `cc_mid_generator` |

Состояния (`:108-113`):

```
CC_CONNECTING ──> CC_RUNNING ──> CC_ZOMBIE
       │              │
       └──> CC_ERROR <┘
```

`CC_ZOMBIE` — соединение, которое ещё существует как объект, но больше не
обслуживает запросы. `cc_broken` отмечает разрыв, замеченный потоком чтения.

### `cifs_tree_t` (`:156-174`)

Подключенный ресурс (share). Держит `ct_tid`, имя ресурса, **счётчик ссылок**
`ct_refcount`, собственную условную переменную и состояние из трёх значений:
`CT_CONNECTING`, `CT_RUNNING`, `CT_ERROR`.

Комментарий в коде фиксирует важное: `ct_cc` — не просто указатель, дерево
**держит ссылку в соединении** (`:157`).

### Глобальное состояние

`cifs_connections` — список всех соединений, `smb_global_mutex` — единственный
мьютекс, защищающий и список, и поля соединений, и деревья (`:66`, `:67`).

---

## 2. Поток на соединение

У каждого соединения свой поток (`cc_thread`), читающий NBT-кадры. Запросы
устроены асинхронно: отправитель кладёт `nbt_req_t` в
`cc_pending_nbt_requests`, помечает его идентификатором `nr_mid` и засыпает на
`cc_cond`; поток чтения находит запрос по `mid` в пришедшем ответе, заполняет
`nr_response` и будит ожидающих.

Отсюда два следствия:

* **Несколько запросов могут быть в полёте одновременно** — этим пользуется
  чтение файлов; предел задаёт согласованный с сервером `cc_max_mpx_count`.
* Ожидание ограничено `NBT_TIMEOUT` = 30000 мс (`:69`, `:1181`), после чего
  ожидающий получает ошибку, а не виснет.

Идентификаторы выдаёт `cc_mid_generator`; поле `pid` используется как метка
назначения — периодический `SMB_ECHO` отправляется с `pid = 3`, чтобы его
ответ отличался от прочих (`:2747`).

---

## 3. Таймер поддержания сессии

`cc_timer` взводится на `SMB_ECHO_INTERVAL` (`:1119`) и вызывает
`cifs_periodic` (`:2731`), который шлёт `SMB_ECHO` с двумя байтами `0x13 0x37`.
Флаг `cc_wait_for_ping` отмечает, что ответа ещё ждут: неполученный ответ —
признак мёртвого соединения.

Это единственная периодическая активность клиента. Ни соединения, ни деревья не
закрываются по истечении времени простоя.

---

## 4. Разрушение

```
smb_close(fh)                     ← последний файл дерева
   └─ cifs_release_tree(ct, full)
        ├─ ct_refcount--
        ├─ refcount > 0 или !full ─> выход, дерево живёт
        └─ LIST_REMOVE(ct) ─> cifs_release_connection(cc)
                                  └─ cc_refcount-- ─> cifs_maybe_destroy(cc)
```

`cifs_release_tree` (`:1209-1226`) освобождает дерево **только когда счётчик
дошёл до нуля и запрошено полное освобождение** (`:1218-1221`). Параметр `full`
принудительно выставляется в 1, если соединение помечено
`CC_F_NON_INTERACTIVE` (`:1212-1213`): пробное обращение не оставляет за собой
подключённых ресурсов.

Первое действие функции — `cc_auto_close = 0` (`:1215`), то есть само по себе
освобождение отменяет автозакрытие.

`cifs_disconnect` (`:1232-1248`) идёт по списку деревьев и **останавливается на
первом, у которого ненулевой счётчик** (`:1237-1240`), не разрушив ничего
дальше и отпустив мьютекс. Это делает функцию безопасной при живых
пользователях, но означает, что она может завершиться, не закрыв соединение.

Разрушение соединения выполняет `cifs_maybe_destroy`, и происходит оно только
при нулевом `cc_refcount`.

---

## 5. Что из этого следует

**Ошибка протокола и повреждённый ответ разрушают разное.** `check_smb_error`
(`:1568-1590`) при ненулевом коде ошибки отпускает дерево с `full = 0` —
соединение и ресурс переживают неудачную операцию; при коротком пакете
вызывает с `full = 1`, и это рвёт всё, что не держат другие пользователи.
Различие намеренное: искажённый кадр означает, что состоянию потока чтения
доверять нельзя.

**Один мьютекс на весь бэкенд.** `smb_global_mutex` защищает список соединений,
их поля и деревья. Длительные операции выполняются с отпущенным мьютексом —
поэтому в коде встречается характерный приём: отпустить мьютекс перед
ожиданием и взять снова после.

**Соединение переживает файл, а файл — операцию.** Закрытие последнего файла не
закрывает дерево, если на него есть другие ссылки; закрытие последнего дерева
не закрывает соединение, пока `cc_refcount` не дошёл до нуля. Проверка
«закрыл файл — сокет закрылся» провалится не из-за дефекта.

**`fap_no_parking`.** Протокол объявляет `smb_no_parking` (`:2943`), то есть
сообщает вышележащему слою, что его дескрипторы нельзя откладывать в общий пул
на паузе воспроизведения. Причина в том же: состояние сессии живёт в потоке
соединения, а не в дескрипторе.
