# Спецификация FTP-клиента в Movian

> **Провенанс.** Каждое утверждение ниже выведено чтением
> `src/fileaccess/fa_ftp.c` и `src/fileaccess/ftpparse.c` на `movian6` @
> `80e6c3617` (2026-08-15) и снабжено ссылкой на строку. Ничего не перенесено
> из более ранних черновиков: они содержали девятнадцать неверных утверждений и
> были отклонены (PR #194, задача #196).

Функциональная спецификация встроенного FTP-клиента. Документ описывает то, что
код делает сегодня, а не то, что предписывает RFC 959.

---

## 1. Регистрация и область применения

Протокол регистрируется как `fa_protocol_ftp` (`fa_ftp.c:897-909`):

| Поле | Значение |
|---|---|
| `fap_name` | `ftp` |
| `fap_flags` | `FAP_INCLUDE_PROTO_IN_URL`, `FAP_ALLOW_CACHE` |
| Обработчики | `fap_scan`, `fap_open`, `fap_close`, `fap_read`, `fap_seek`, `fap_fsize`, `fap_stat` |

**Клиент строго только для чтения.** В таблице нет `fap_write`, `fap_unlink`,
`fap_rmdir`, `fap_makedir` и `fap_rename`, поэтому запись, удаление,
переименование и создание каталогов недоступны — не «не реализованы и вернут
ошибку», а не существуют как точки входа.

Порт по умолчанию — `21`, подставляется когда URL его не задаёт
(`fa_ftp.c:385-386`).

---

## 2. Авторизация

Учётные данные берутся из связки ключей по идентификатору
`ftp://<host>:<port>` (`fa_ftp.c:232`), причём порт входит в него всегда, даже
для 21.

Цикл входа (`fa_ftp.c:234-263`):

1. `keyring_lookup()` вызывается без `KEYRING_QUERY_USER` на первой итерации и с
   ним на всех последующих (`:241`), то есть сохранённые данные пробуются молча,
   а спрашивают только после отказа.
2. `KEYRING_NOT_FOUND` уводит на следующую итерацию, где пользователя уже
   спросят; `KEYRING_USER_REJECTED` завершает подключение с «Rejected by user».
3. Отправляются `USER` и `PASS`; цикл повторяется, **пока `PASS` не ответит
   `230`** (`:261`).

**Анонимного входа не существует.** Ни `anonymous`, ни какого-либо пароля по
умолчанию в коде нет; при отсутствии записи в связке ключей клиент спрашивает
пользователя.

**Ограничения числа попыток нет.** Единственный выход из цикла, кроме успеха, —
отказ пользователя или флаг `non_interactive`, который прерывает работу начиная
со второй итерации (`:236-237`). Поэтому фоновое сканирование
(`FA_NON_INTERACTIVE`) не может ни спросить пароль, ни зациклиться: оно делает
ровно одну молчаливую попытку.

После успешного входа один раз отправляется `TYPE I`, и ответ обязан быть `200`
(`:265-270`). **Режим передачи устанавливается на соединение, а не на файл**;
`TYPE A` клиент не отправляет никогда.

---

## 3. Пул соединений

Управляющие соединения переиспользуются между операциями
(`fa_ftp.c:38`, `:185-208`, `:302-315`).

* Ключ поиска — пара «хост + порт» (`:186`).
* При освобождении соединение получает `fc_expire = сейчас + 10 000 000` мкс,
  то есть **10 секунд**, и кладётся в список (`:310-312`).
* При повторном взятии из списка соединение старше срока проверяется командой
  `NOOP`; ответ обязан быть `200`, иначе соединение закрывается и поиск
  начинается заново (`:195-203`).
* Соединение, на котором остался незавершённый канал данных, в пул **не
  возвращается**: `ftp_close` выставляет `drop = 1` (`:604-609`).

---

## 4. Канал данных

Единственный поддерживаемый режим — **пассивный** (`ftp_open_data_transfer`,
`fa_ftp.c:323-350`):

1. Отправляется `PASV`, ответ обязан быть `227` (`:329-333`).
2. Адрес разбирается строгим шаблоном
   `Entering Passive Mode (%d,%d,%d,%d,%d,%d)` (`:335-338`) — сервер, который
   формулирует ответ `227` иначе, приводит к отказу открыть канал.
3. Соединение открывается с таймаутом `5000` мс (`:342`).

`EPSV`, `PORT` и `EPRT` не отправляются нигде. Следствия: **сервер, доступный
только по IPv6, не поддерживается**, как и сервер, требующий активного режима.

## 5. Операции VFS

| Функция | Что уходит на сервер | Примечание |
|---|---|---|
| `ftp_open` (`:578-591`) | `SIZE` | Канал данных **не** открывается и `RETR` не отправляется. |
| `ftp_read` (`:618-672`) | при первом чтении: `PASV`, `REST <pos>`, `RETR` | Ленивое начало передачи, см. ниже. |
| `ftp_seek` (`:678-731`) | ничего | Только арифметика над `ff_fpos`; открытый канал закрывается. |
| `ftp_fsize` (`:737-746`) | `SIZE`, если размер ещё не известен | Далее отдаёт кэш `ff_size`. |
| `ftp_stat` (`:765-880`) | `MLST`, при отказе — `LIST` родительского каталога | См. раздел 6. |
| `ftp_scandir` (`:562-572`) | `PASV`, `LIST` | Всегда `LIST`, см. раздел 7. |
| `ftp_close` (`:597-612`) | ничего | Закрывает канал данных и дочитывает финальный ответ. |

### Ленивое начало передачи

`ftp_open` только заполняет структуру и спрашивает размер. Передача начинается
при первом `ftp_read`, когда `ff_xfer == NULL` (`:633-650`): открывается
пассивный канал, отправляется `REST <позиция>` (ожидается `350`), затем `RETR`
(ожидается `150`). Открытый дескриптор поэтому **не означает, что файл
существует и читаем** — ошибка появится на первом чтении.

### Позиционирование

`ftp_seek` не отправляет `REST` сам (`:678-731`). Он закрывает канал данных,
если тот был открыт, дочитывает финальный ответ и просто меняет `ff_fpos`.
Новое смещение уходит на сервер при следующем `ftp_read`. Поэтому подряд идущие
seek стоят одного разрыва канала, а не нескольких.

### Отсутствие размера делает файл пустым

`ftp_read` обрезает запрошенный объём по `ff_size` (`:627-631`). Если `SIZE` не
дал `213`, `ff_size` остаётся `-1` (`:394`, `:419-421`), выражение
`ff_fpos + size > ff_size` истинно всегда, `size` становится отрицательным и
**каждое чтение возвращает `0`, то есть конец файла**. Сервер без поддержки
`SIZE` выглядит как сервер с пустыми файлами, а не как ошибка.

## 6. `stat`

`ftp_stat` (`fa_ftp.c:765-880`) сначала пробует `MLST`, если на этом соединении
не выставлен флаг `fc_no_mlst`:

* ответ `550` → ошибка (`:785-786`);
* ответ, не начинающийся с `250-`, **навсегда** выключает `MLST` для этого
  соединения (`:826-830`) — не на одну операцию;
* из строки берутся `type=`, `modify=` и `size=` (`:792-794`). Требуются
  одновременно `type` и `modify`; `size` обязателен только для `type=file`
  (`:796-806`);
* `type=cdir` и `type=dir` дают `CONTENT_DIR`, `type=file` — `CONTENT_FILE`,
  всё остальное считается ошибкой (`:802-809`);
* время разбирается как 14 цифр `YYYYMMDDhhmmss` в UTC (`:811-817`).

Запасной путь, когда `MLST` недоступен: пустой путь считается каталогом
(`:832-833`), иначе выполняется `LIST` **родительского** каталога, и запись
ищется по имени (`:855-873`). То есть `stat` одного файла на сервере без `MLST`
стоит полного листинга его каталога.

Команды `SIZE` и `MDTM` в `ftp_stat` не используются.

## 7. Листинг каталога

`ftp_list_dir` (`fa_ftp.c:550-556`):

```c
if(0)
  return ftp_list_dir_STAT(fc, path, fd);
return ftp_list_dir_LIST(fc, path, fd);
```

**Всегда используется `LIST`.** Вариант через `STAT` существует
(`:520-544`), но выключен константным условием. Реализация `MLSD`
(`:424-437`) находится под `#if 0` и в текущем виде не скомпилировалась бы —
она ссылается на переменную `ff`, которой в её области видимости нет.

`ftp_list_dir_LIST` (`:483-514`) открывает пассивный канал, отправляет
`LIST <путь>` (или `LIST .` для пустого пути), разбирает каждую строку через
`ftpparse`, закрывает канал и затем **дочитывает управляющий канал до
окончательного кода**: ответы меньше `200` пропускаются, `400` и выше означают
ошибку (`:503-513`).

Тип записи определяется полем `flagtrycwd` разбора, а не именем или правами
(`:458-461`); размер и время модификации берутся оттуда же и сразу
проставляются в запись каталога как готовые (`fde_statdone = 1`, `:470-473`),
так что отдельный `stat` на элемент списка не выполняется.

## 8. Ошибки

**Отображения кодов ответа FTP в `errno` не существует.** В `fa_ftp.c` нет ни
одного `EACCES`, `ENOENT`, `ECONNRESET` или `ENOTSUP`. Наружу уходят только:

| Функция | Значение при ошибке |
|---|---|
| `ftp_stat` | `FAP_ERROR` (`:773`, `:879`) |
| `ftp_scandir` | `1` (`:567`) |
| `ftp_read`, `ftp_seek`, `ftp_fsize` | `-1` |
| `ftp_open` | `NULL` с текстом в `errbuf` |

Текстовые сообщения формируются только на этапе подключения: неверное
приветствие (`:222`), отказ пользователя (`:250`), неудача `TYPE I` (`:268`).

Отдельно обрабатывается код `412`: `fc_read_result` считает его разрывом
соединения и возвращает `-1` (`:130-133`). Многострочные ответы читаются до
строки, где после кода нет дефиса (`:111-116`).

---

## 9. Ограничения

* **Таймаут подключения:** `5000` мс — одинаково для управляющего канала
  (`:210`) и канала данных (`:342`).
* **Время жизни соединения в пуле:** 10 секунд до обязательной проверки
  `NOOP` (`:310`).
* **Длина имени хоста:** 128 байт, пути — 1024 байта; оба буфера фиксированы в
  `ftp_file_t` (`:76-77`).
* **Согласования кодировки нет.** `OPTS UTF8 ON` не отправляется, ответ на
  `FEAT` не разбирается; команда `FEAT` вообще не отправляется клиентом.
* **Диагностика** включается флагом `gconf.enable_ftp_client_debug` и печатает
  каждую отправленную и принятую строку (`:81-84`).
