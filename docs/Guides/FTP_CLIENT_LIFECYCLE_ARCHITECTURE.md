# Архитектура жизненного цикла FTP-клиента

> **Провенанс.** Выведено чтением `src/fileaccess/fa_ftp.c` на `movian6` @
> `80e6c3617` (2026-08-15); каждое утверждение снабжено ссылкой на строку.
> Функциональная сторона — в `FTP_CLIENT_SPECIFICATION.md`.

Документ описывает структуры, владение ими и порядок разрушения. Главная его
мысль в том, что у клиента **два независимых времени жизни**: управляющее
соединение живёт дольше файла и переживает его закрытие, а канал данных короче
файла и может открываться и закрываться под ним несколько раз.

---

## 1. Структуры

### `ftp_connection_t` (`fa_ftp.c:45-59`)

Управляющее соединение. Содержит ровно семь полей:

| Поле | Назначение |
|---|---|
| `fc_link` | член глобального списка припаркованных соединений |
| `fc_id` | номер для диагностики, из `id_tally` (`:215`) |
| `fc_tc` | сокет управляющего канала |
| `fc_hostname`, `fc_port` | ключ поиска в пуле |
| `fc_url` | префикс для построения URL записей каталога |
| `fc_expire` | момент, после которого нужна проверка `NOOP` |
| `fc_no_mlst` | сервер не понял `MLST`, больше не пробовать |

Чего в структуре **нет**, хотя это часто предполагают: логина, пароля,
признака авторизованности, текущего каталога и списка расширений сервера.
Учётные данные существуют только как локальные переменные внутри `fc_connect`
(`:226-227`) и после входа не сохраняются. Текущего каталога нет, потому что
клиент не отправляет `CWD` — все пути передаются целиком в каждой команде.

Из «расширений сервера» запоминается ровно один факт — `fc_no_mlst`.

### `ftp_file_t` (`fa_ftp.c:65-79`)

Открытый файл. Помимо `fa_handle_t`:

| Поле | Назначение |
|---|---|
| `ff_fc` | занятое управляющее соединение, может быть `NULL` |
| `ff_xfer` | сокет канала данных, `NULL` пока передача не начата |
| `ff_fpos` | позиция чтения |
| `ff_size` | размер, `-1` пока неизвестен |
| `ff_hostname[128]`, `ff_pathbuf[1024]`, `ff_pathx`, `ff_port` | разобранный URL |

`ff_pathx` указывает внутрь `ff_pathbuf`, пропуская ведущий `/` (`:388-391`).
Это не отдельная строка, а смещение — освобождать её нельзя.

### Глобальное состояние

`ftp_connections` — список припаркованных соединений, `ftp_global_mutex` —
его мьютекс, `id_tally` — счётчик номеров (`:38-40`). Мьютекс инициализируется
в `ftp_init` вместе с таблицами `ftpparse` (`:886-891`).

## 2. Жизненный цикл управляющего соединения

```
     fc_connect ──> [занято файлом] ──> ftp_file_release ──> [припарковано]
         ↑                                                         │
         └──────────── повторное взятие, NOOP если истёк ──────────┘
                                    │
                                    └─ NOOP != 200 ─> fc_disconnect ─> заново
```

**Взятие** (`fc_connect`, `:172-289`). Сначала список просматривается по паре
«хост + порт» (`:185-188`). Найденное соединение немедленно **удаляется из
списка** (`:191`) — то есть занятое соединение в списке не лежит, и повторно
его никто не возьмёт. Если срок истёк, отправляется `NOOP`; ответ, отличный от
`200`, ведёт к `fc_disconnect` и повторному проходу с метки `again` (`:195-203`).

Новое соединение проходит полную последовательность: TCP, приветствие `220`,
цикл авторизации, `TYPE I`. Только после этого заполняются `fc_hostname`,
`fc_port` и `fc_url` (`:272-279`) — **до этого момента структура не пригодна для
поиска в пуле**, что и правильно, поскольку в список она попадёт лишь при
освобождении.

**Освобождение** (`ftp_file_release`, `:295-317`). Параметр `drop` решает
судьбу соединения: при `drop != 0` оно закрывается, иначе получает срок
`+10 секунд` и возвращается в список. Функция начинается с
`assert(ff->ff_xfer == NULL)` (`:300`) — **освобождать файл с открытым каналом
данных запрещено**, и это ответственность вызывающего.

**Разрушение** (`fc_disconnect`, `:159-166`). Освобождает имя хоста и URL,
закрывает сокет, освобождает структуру. Из списка не удаляет: к моменту
вызова соединение уже изъято.

### Как соединение теряется

Три пути, и все три оставляют `ff_fc == NULL` у живого файла:

1. `ftp_seek` получил `-1` при дочитывании результата прерванной передачи
   (`:719-722`);
2. `ftp_close` увидел открытый канал данных и выставил `drop` (`:604-611`);
3. подключение вообще не удалось (`ff_reconnect` вернул ошибку).

Первый случай интересен тем, что файл остаётся пригодным **для чтения и
запроса размера**: и `ftp_read`, и `ftp_fsize` начинаются с `ff_reconnect`
(`:356-366`) и подключаются заново, с новым проходом авторизации.

Но не для закрытия. `ftp_close` разыменовывает `ff->ff_fc->fc_id` в
диагностическом вызове (`:602`) до всякой проверки, поэтому `ftp_close` сразу
после такого `ftp_seek` падает — **при включённом
`gconf.enable_ftp_client_debug`**, потому что аргумент вычисляется только внутри
`FTP_TRACE` (`:81-84`). Задача #203.

## 3. Жизненный цикл канала данных

Канал данных принадлежит файлу, а не соединению, и живёт от первого чтения до
первого события из списка: seek, close, ошибка чтения.

**Открытие** происходит внутри `ftp_read`, когда `ff_xfer == NULL`
(`:633-650`), и только там. Последовательность строго `PASV` → `REST` → `RETR`,
и каждый шаг проверяется по коду (`227`, `350`, `150`).

**Закрытие** выполняется в трёх местах, и во всех трёх после `tcp_close`
обязательно дочитывается финальный ответ управляющего канала:

| Место | Что делает с соединением |
|---|---|
| `ftp_read`, ошибка чтения (`:656-661`) | дочитывает результат, соединение сохраняет |
| `ftp_seek` (`:711-726`) | дочитывает; `-1` → рвёт соединение, `>= 500` → ошибка |
| `ftp_close` (`:604-609`) | дочитывает и **всегда** помечает соединение на снос |

Порядок здесь существенный: сначала `tcp_close` канала данных, затем чтение
результата. Обратный порядок повис бы, потому что сервер отправляет финальный
`226` только после того, как канал данных закрыт.

Асимметрия последней строки таблицы намеренна. Прерванная на середине передача
оставляет управляющий канал в состоянии, о котором клиент не может судить
дёшево, поэтому такое соединение не переиспользуется.

## 4. Порядок разрушения

```
ftp_close(fh)
   ├─ ff_xfer != NULL ─> tcp_close(ff_xfer) ─> fc_read_result() ─> drop = 1
   └─ ftp_file_release(ff, drop)
         ├─ assert(ff_xfer == NULL)
         ├─ drop ? fc_disconnect(fc) : парковка со сроком +10 с
         └─ free(ff)
```

Клиент не имеет ни своего потока, ни таймера. Припаркованные соединения не
закрываются по расписанию: они живут в списке до тех пор, пока их не возьмут
снова, и проверка `NOOP` при взятии — единственный момент, когда обнаруживается
разрыв со стороны сервера. Соединение к серверу, к которому больше не
обращаются, остаётся открытым.

---

## 5. Потокобезопасность

`ftp_global_mutex` защищает **только список припаркованных соединений**
(`:183-192`, `:311-313`). Он не защищает ни `ftp_connection_t`, ни
`ftp_file_t`: за пределами списка соединение принадлежит ровно одному файлу,
поскольку изымается из списка под мьютексом и возвращается туда же.

Отсюда правило для вызывающего: **один `ftp_file_t` не должен использоваться
из двух потоков одновременно**. Ни `ff_fpos`, ни `ff_xfer`, ни цепочка команд
на управляющем канале ничем не сериализованы.

Счётчик `id_tally` атомарный (`:215`), потому что номера раздаются при
подключении, которое может идти параллельно для разных хостов.
