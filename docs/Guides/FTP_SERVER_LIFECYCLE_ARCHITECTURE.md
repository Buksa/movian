# Архитектура жизненного цикла FTP-сервера

> **Провенанс.** Выведено чтением `src/networking/ftp_server.c` на `movian6` @
> `80e6c3617` (2026-08-15); каждое утверждение снабжено ссылкой на строку.
> Функциональная сторона — в `FTP_SERVER_SPECIFICATION.md`.

Три уровня времени жизни, и они не вложены друг в друга так, как можно
предположить: слушатель принадлежит asyncio, сессия — своему потоку, а канал
данных — одной команде.

---

## 1. Слушатель

Единственная точка управления — `enable_disable()` (`ftp_server.c:954-972`),
которую дёргают оба обработчика настроек: `set_enable` и `set_port`
(`:978-993`). Настройки имени и пароля слушателя не касаются — они лишь
переписывают глобальные строки (`:998-1008`).

```
порт != 0 && включён ?
   ├─ да: уже слушаем этот порт ─> ничего не делать
   │      слушаем другой ────────> asyncio_del_fd, затем asyncio_listen
   └─ нет: слушаем ─────────────> asyncio_del_fd, ftp_server_fd = NULL
```

Проверка `asyncio_get_port(ftp_server_fd) == ftp_server_port` (`:957`) делает
функцию идемпотентной: повторное применение той же настройки не роняет
существующие сессии. Смена порта, наоборот, снимает слушатель и поднимает
новый — **уже установленные сессии при этом не разрываются**, они живут в своих
потоках и о слушателе ничего не знают.

Обе настройки объявлены с `SETTINGS_INITIAL_UPDATE` (`:1029`, `:1037`), поэтому
`enable_disable()` вызывается при старте приложения с сохранёнными значениями, а
не только при изменении пользователем. Обработчики выполняются на курьере
`asyncio_courier` (`:1034`), то есть в потоке asyncio — там же, где живёт
слушающий дескриптор.

---

## 2. Сессия

`ftp_accept` (`:928-948`) вызывается asyncio на каждое входящее соединение и
делает ровно четыре вещи: создаёт `ftp_connection_t`, запоминает локальный и
удалённый адреса, задаёт начальное состояние и **порождает отсоединённый
поток**:

```c
set_wd(fc, "/");
set_type(fc, 'A');
hts_thread_create_detached("FTP-session", ftp_session, fc, THREAD_PRIO_MODEL);
```

Начальный тип передачи — `A`, хотя на саму передачу тип не влияет (см.
спецификацию, раздел 6). Начальный каталог — корень.

Поток отсоединённый: его никто не ждёт и не может прервать. **Средства
закрыть сессию извне не существует** — выключение сервера снимает слушатель, но
уже работающие сессии продолжаются до тех пор, пока клиент не отключится сам.

`ftp_session` (`:863-923`) — цикл над строками управляющего канала:

1. `tcp_read_line`; ошибка чтения выходит из цикла;
2. строка делится по первому пробелу, лишние пробелы аргумента съедаются;
3. линейный поиск по таблице из 22 команд, регистронезависимо;
4. проверяются флаги: нужна авторизация → `530`, нужны аргументы → `500`;
5. обработчик возвращает ненулевое значение → цикл прерывается.

Ненулевое возвращает только `cmd_QUIT` (`:210`), поэтому нормальный выход из
сессии — либо `QUIT`, либо разрыв со стороны клиента. Переменная `r` начинается
с `-1`, и это значение отличает «команда не найдена» от «команда вернула 0»
(`:887`, `:909-911`).

## 3. Состояние сессии

`ftp_connection_t` (`:38-61`) целиком принадлежит своему потоку и после
`ftp_accept` не разделяется ни с кем:

| Поле | Время жизни |
|---|---|
| `fc_tc` | всё время сессии |
| `fc_authorized` | сбрасывается каждой командой `USER` (`:221`) |
| `fc_username` | от `USER` до неудачного `PASS` или конца сессии |
| `fc_wd` | от `ftp_accept` («/») до конца, меняется только `CWD` |
| `fc_type`, `fc_eol` | задаются `TYPE`; `fc_eol` не читается нигде |
| `fc_accept_socket` | от `PASV` до `accept` или следующего `PASV` |
| `fc_pending_RNFR` | от `RNFR` до `RNTO` |
| `fc_local_addr`, `fc_remote_addr` | всё время сессии |

Глобальных данных две строки — `ftp_username` и `ftp_password` (`:69-70`).
Они читаются из потока сессии, а пишутся из потока asyncio при изменении
настроек, без блокировки. Практическое следствие: смена учётных данных во время
работы применяется к следующей проверке `PASS`, а уже авторизованные сессии
своих прав не теряют.

## 4. Канал данных

Живёт внутри одной команды и никогда не переживает её.

```
PASV ──> socket() + bind(0.0.0.0:0) + listen(fd, 1) ──> fc_accept_socket
                                                              │
LIST/RETR/STOR ──> get_data_channel() ──> accept() ──> close(fc_accept_socket)
                                                              │
                                          tcp_close(tc) в конце команды
```

`cmd_PASV` (`:413-453`) при повторном вызове **закрывает предыдущий слушающий
сокет** (`:412-415`), поэтому два `PASV` подряд не оставляют утечки, но и
отменяют первый анонс.

`get_data_channel` (`:463-482`) закрывает слушающий сокет сразу после `accept`
и сбрасывает `fc_accept_socket` в `-1`. Отсюда правило: **один `PASV` — одна
передача**. Клиент, который анонсирует пассивный режим один раз и пытается
выполнить две команды с данными, на второй получит `425`.

## 5. Порядок разрушения

```
ftp_session, выход из цикла
   ├─ tcp_close(fc_tc)
   ├─ free(fc_username)
   ├─ free(fc_pending_RNFR)
   ├─ free(fc_wd)
   ├─ fc_accept_socket != -1 ─> close(fc_accept_socket)
   └─ free(fc)
```

(`:915-922`). Открытый канал данных здесь не закрывается, и это не упущение:
`tcpcon_t` канала — локальная переменная команды, и любая из трёх команд с
данными закрывает его до возврата, в том числе на путях ошибок.

Незакрытым может остаться только **слушающий** сокет от `PASV`, за которым
не последовала команда передачи, — его и снимает предпоследняя строка.

---

## 6. Что из этого следует для тестирования

* Сессии переживают выключение сервера, поэтому проверка «выключил — соединения
  разорвались» провалится не из-за дефекта.
* Смена порта не трогает существующие сессии, но снимает и поднимает
  слушатель — проверять надо новые подключения, а не старые.
* Все файловые операции идут через `fa_protocol_vfs` с `FA_NON_INTERACTIVE`
  (`:79-80`, `:143-144`), поэтому сценарий с хранилищем, требующим ввода
  пароля, не «зависнет в ожидании» — он вернёт ошибку.
* Сетевые проверки этого сервера выполняются со стенда, а не с машины
  разработки: при зеркальной сетевой модели WSL проба собственного порта хоста
  читается как отказ.
