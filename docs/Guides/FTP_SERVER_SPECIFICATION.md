# Спецификация встроенного FTP-сервера Movian

> **Провенанс.** Каждое утверждение выведено чтением
> `src/networking/ftp_server.c` на `movian6` @ `80e6c3617` (2026-08-15) и
> снабжено ссылкой на строку. Ничего не перенесено из более ранних черновиков
> (PR #194 отклонён, задача #196).

---

## 1. Настройки

Четыре настройки в разделе «Сеть» (`ftp_server.c:1027-1062`):

| Настройка | Хранилище | Тип | По умолчанию |
|---|---|---|---|
| Enable FTP server | `ftpserver` / `enable` | булев | `0` — **выключен** (`:1031`) |
| Server TCP port | `ftpserver` / `port` | строка | `2121` (`:1040`) |
| Username | `ftpserver` / `username` | строка | **пусто** (`:1048`) |
| Password | `ftpserver` / `password` | строка | **пусто** (`:1057`) |

Слушатель поднимается только когда порт ненулевой **и** сервер включён
(`enable_disable`, `:955`). Порт `2121` выбран непривилегированным: обычный
процесс не может занять `21` без прав.

## 2. Авторизация

> **Пустое имя пользователя отключает проверку целиком.** Это заводское
> значение настройки.

`cmd_PASS` (`ftp_server.c:232-252`):

```c
if(*ftp_username &&
   (strcmp(fc->fc_username, ftp_username) || strcmp(args, ftp_password))) {
  ftp_write(fc, 530, "Login incorrect.");
```

Сравнение целиком стоит за проверкой `*ftp_username`. Пока настройка «Username»
пуста, ветка не выполняется, и **любые `USER`/`PASS` дают `230 User logged in`**
с полным доступом, включая запись и удаление. Сервер выключен по умолчанию,
поэтому это не открытая наружу дыра — но включивший его пользователь получает
анонимный доступ, если не заполнит имя.

Порядок команд: `USER` сбрасывает признак авторизации, запоминает имя и отвечает
`331` (`:219-227`). `PASS` без предшествующего `USER` даёт `503`
(`:235-238`). Неверная пара очищает запомненное имя, так что повтор `PASS`
снова даст `503`, а не вторую попытку.

## 3. Таблица команд

22 записи (`ftp_server.c:827-852`). Сопоставление регистронезависимое
(`:889`), аргументом считается всё после первого пробела (`:878-882`).

| Команда | Флаги | Ответ при успехе |
|---|---|---|
| `QUIT` | — | `221`, соединение закрывается |
| `USER` | нужны аргументы | `331` |
| `PASS` | нужны аргументы | `230` / `530` |
| `SYST` | **нужна авторизация** | `215 UNIX Type: L8` |
| `FEAT` | **нужна авторизация** | `211` со списком `UTF8`, `SIZE` |
| `PWD`, `XPWD` | нужна авторизация | `257` |
| `CWD`, `XCWD` | нужна авторизация | `250` |
| `PASV` | нужна авторизация | `227` |
| `LIST` | нужна авторизация | `130`, затем `226` |
| `SIZE` | авторизация + аргументы | `213` |
| `TYPE` | авторизация + аргументы | `200` |
| `RETR` | авторизация + аргументы | `150`, затем `226` |
| `STOR` | авторизация + аргументы | `150`, затем `226` |
| `MKD`, `XMKD` | авторизация + аргументы | `257` |
| `DELE` | авторизация + аргументы | `250` |
| `RMD`, `XRMD` | авторизация + аргументы | `250` |
| `RNFR`, `RNTO` | авторизация + аргументы | `350`, затем `250` |
| `OPTS` | авторизация + аргументы | зависит от аргумента |

**`SYST` и `FEAT` требуют авторизации** (`:835-836`). Клиент, спрашивающий
возможности сервера до входа — а так поступают многие, — получит
`530 Please login first`, а не список.

Неизвестная команда даёт `500 Command not understood` (`:909-911`). Команда без
обязательного аргумента — `500 Arguments required` (`:896-897`).

Сервер **пишущий**: `STOR`, `DELE`, `MKD`, `RMD`, `RNFR`/`RNTO` реализованы и
работают через `fa_protocol_vfs`.

## 4. Пути

`construct_path` (`ftp_server.c:309-359`) строит абсолютный путь из текущего
каталога сессии и аргумента:

* `.` — текущий каталог; `..` — на уровень вверх, из корня отвечает `550`
  (`:314-332`);
* аргумент отвергается, если содержит любой из символов `\ : ? * | < >`
  (`:336-340`) или подстроку `/..` (`:343-345`) — с ответом `550`;
* абсолютный путь берётся как есть, относительный присоединяется к текущему
  каталогу (`:348-353`);
* хвостовые `/` срезаются (`:356-358`).

Проверка на `/..` строковая, поэтому она ловит подъём в середине пути, а
отдельный аргумент `..` обрабатывается раньше отдельной веткой.

> **Отказ выносится, но не соблюдается.** Ненулевой возврат `construct_path`
> проверяет **только `cmd_CWD`** (`:376`). `LIST`, `SIZE`, `RETR`, `STOR`,
> `MKD`, `DELE`, `RMD`, `RNFR` и `RNTO` его игнорируют и продолжают работу с
> буфером `pathbuf`, который на этом пути **остался незаполненным** — функция
> пишет `550` и возвращается, не коснувшись `dst`. Клиент получает второй ответ
> вслед за `550`, а VFS-операция выполняется по содержимому неинициализированного
> массива, в том числе в разрушающих командах.

## 5. Канал данных

Только пассивный режим. `get_data_channel` (`:463-482`) умеет единственное:
принять соединение на сокете, созданном `PASV`. При его отсутствии возвращается
`NULL`, и вызывающий отвечает `425 Can't build data connection`. Команд `PORT`,
`EPRT` и `EPSV` в таблице нет.

`cmd_PASV` (`:413-453`) закрывает предыдущий слушающий сокет, создаёт новый,
привязывает его к нулевому адресу и порту, ставит `listen(fd, 1)` и сообщает
клиенту **адрес, на который пришло управляющее соединение** (`fc_local_addr`),
и назначенный ядром порт. В коде на этом месте стоит замечание автора, что
привязываться следовало бы к тому же интерфейсу, а не ко всем.

Очередь слушателя — один клиент; сокет закрывается сразу после `accept`
(`:474-475`).

## 6. Передача

`RETR` (`:588-634`) и `STOR` (`:641-686`) устроены одинаково: открыть файл
через VFS, ответить `150`, **затем** получить канал данных, перекачать буфером
`65536` байт, закрыть, ответить `226` или `400` при ошибке.

> **`400` отвечает только на отказ приёмника.** В `RETR` флаг `error`
> выставляется исключительно при неудаче `tcp_write_data` (`:617-620`), в
> `STOR` — при неудаче `fa_write` (`:670-673`). Ошибка **источника** —
> отрицательный `fa_read` в `RETR` или `tcp_read_data_nowait` в `STOR` —
> завершает цикл с нулевым `error`, и клиент получает `226 Transfer complete`
> на оборванной передаче.

Порядок здесь стоит заметить: `150` уходит до того, как канал данных получен,
поэтому клиент может увидеть `150`, а следом `425`.

**`TYPE A` не преобразует переводы строк.** `set_type` заполняет поле `fc_eol`
(`:165-173`), но **ни один путь передачи его не читает**: `RETR` копирует байты
из `fa_read` в сокет, `STOR` пишет принятые байты через `fa_write` без единой
подстановки. Поле мертво — в нём даже сохранена опечатка `"\n'"` для
двоичного режима, которая ни на что не влияет именно потому, что значение
никогда не используется.

`LIST` (`:489-556`) отдельный: он сначала получает канал, потом сканирует
каталог, и **не** проходит через `get_data_channel` дважды. Аргументы вида
`-la`, которые клиенты по традиции передают как флаги `ls`, отбрасываются
(`:505-517`). Строки формируются с фиксированными владельцем и датой:

```
%crwx------  1 nobody nobody %10llu May  5 11:20 %s
```

То есть **права, владелец и дата в листинге — константы**, реальны только тип
(каталог или файл), размер и имя (`:545-551`). Ответ открывается кодом `130` (`:537`),
а не `150`.

## 7. Ограничения

* Один поток на соединение, `hts_thread_create_detached("FTP-session", ...)`
  с приоритетом `THREAD_PRIO_MODEL` (`:944-945`). Ограничения числа
  одновременных сессий нет.
* Командная строка — до 1024 байт (`:877`), ответ сервера — до 2048 (`:181`).
* Буфер передачи — 65536 байт, выделяется и освобождается на каждую команду
  (`:610`, `:665`).
* Диагностика включается флагом `gconf.enable_ftp_server_debug` и печатает
  каждую принятую и отправленную строку (`:194-196`, `:877-878`).
* `FA_NON_INTERACTIVE` передаётся **только** обёртками `ftp_server_stat`
  (`:79-80`) и `ftp_server_scandir` (`:143-144`). `ftp_server_open` (`:87-92`),
  через который идут `RETR` и `STOR`, передаёт `0` или `FA_WRITE`, поэтому
  хранилище, требующее учётных данных, может уйти в интерактивную авторизацию
  и остановить сессию FTP.
